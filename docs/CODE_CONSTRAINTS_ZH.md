# CODE_CONSTRAINTS_ZH.md
# 物品管理系统 · 代码级强约束规范（中文版 · 给 CODEX / AI 用）

## 0. 文档定位（必须首先阅读）

本文档用于定义本项目的**代码级不可突破约束**。

这些规则：
- 不是建议
- 不是最佳实践
- 而是 **硬性约束（Hard Constraints）**

任何违反本文档的代码，均视为 **无效代码 / Bug**。

优先级顺序：
代码约束 > 功能实现 > 性能优化 > 代码风格

---

## 1. 全局上下文约束（Global）

### CC-1【强制】scene_id 全链路存在
- 所有业务实体 **必须包含 `scene_id` 字段**
- 所有查询 **必须显式受 `scene_id` 约束**
- 所有写入操作 **必须显式设置 `scene_id`**

❌ 禁止：
- 默认场景
- 不带 scene_id 的查询
- 硬编码 scene_id
- 跨场景读写

✅ 必须：
- scene_id 从请求 Header 获取
- scene_id 写入统一上下文
- 在任何业务逻辑前完成 scene 校验

---

### CC-2【强制】禁止绕过 SceneContext
所有业务逻辑 **只能** 从统一上下文获取 scene_id。

❌ 禁止：
- 方法参数层层传 scene_id
- 从 Session / 全局变量 / 常量中取 scene_id

✅ 必须：
- 使用 SceneContext（ThreadLocal / RequestScope）
- SceneContext.getSceneId() 是唯一来源

---

## 2. 分层结构约束（Architecture）

### CC-3【强制】严格分层，禁止越权访问

依赖方向必须为：

Controller  
→ Application Service  
→ Domain Model  
→ Repository / Infrastructure

❌ 禁止：
- Controller 直接访问 Repository
- Domain 访问 HTTP / 数据库 / 缓存
- Repository 内写业务规则

---

### CC-4【强制】Controller 必须是“瘦”的
Controller 只允许做：
- 请求参数校验
- Header 提取
- 调用 Application Service

❌ 禁止：
- 业务判断
- 状态流转
- 权限/规则决策

---

## 3. 领域模型约束（Domain）

### CC-5【强制】领域模型必须是“有行为的”
领域实体必须：
- 封装状态变更
- 使用语义明确的方法名

❌ 禁止：
- 只有 getter/setter 的贫血模型
- 在 Service 中直接修改实体字段

✅ 示例（必须类似）：
- item.moveTo(locationId)
- item.markBorrowed(borrower)

---

### CC-6【强制】物品与位置为弱耦合关系
- 物品允许没有位置（location_id 可为空）
- 删除位置时 **不允许级联删除物品**

❌ 禁止：
- 外键级联删除
- location_id 非空强约束

---

### CC-7【强制】位置树深度不可假设
- 位置层级无限
- 不允许在代码中假设层级数量

❌ 禁止：
- level == 3 这种逻辑
- “房间-柜子-抽屉”写死结构

---

## 4. Repository 层约束

### CC-8【强制】Repository 默认具备场景意识
- Repository 不接受 scene_id 作为参数
- scene_id 由内部统一注入

❌ 禁止：
- 无 scene_id 过滤的查询
- 暴露 scene_id 参数给调用方

---

### CC-9【强制】禁止动态拼接 SQL
- 查询条件必须明确
- 字段名不可动态生成

❌ 禁止：
- 字符串拼 SQL
- 反射构造查询字段

---

## 5. 查询与搜索约束（Findability First）

### CC-10【强制】搜索优先“找得到”
搜索必须：
- 同时命中名称 / 标签 / 备注
- 支持模糊匹配

❌ 禁止：
- 仅精确匹配
- 无结果直接返回空列表

---

### CC-11【强制】查询结果必须包含位置信息
任何返回物品的接口，必须同时返回：
- location_id
- 完整位置路径（直接或计算得到）

❌ 禁止：
- 返回“没有位置上下文”的物品数据

---

## 6. 审计与历史约束

### CC-12【强制】关键操作必须审计
必须记录审计的操作包括：
- 新增 / 修改 / 删除物品
- 移动物品
- 移动位置节点
- 借出 / 归还
- 批量操作

审计信息至少包含：
- scene_id
- 实体类型
- 实体 ID
- 操作类型
- 操作前状态
- 操作后状态

❌ 禁止：
- 静默修改数据
- 以性能为由跳过审计

---

## 7. 借出逻辑约束

### CC-13【强制】借出不等于消失
- 借出状态下物品仍可查询
- 借出状态下物品仍可搜索
- 禁止通过数量变化模拟借出

❌ 禁止：
- quantity - 1 表示借出
- 借出即从列表中移除

---

## 8. API 契约约束

### CC-14【强制】接口必须显式依赖场景
- 每个 API 请求必须携带 `X-Scene-Id`
- 缺失或非法 scene_id 必须直接失败

❌ 禁止：
- 服务端记忆场景
- 使用 Session 保存 scene

---

### CC-15【建议】接口应具备幂等性
- 移动、更新类接口可安全重试
- 重复请求不应破坏状态

---

## 9. 性能与复杂度约束

### CC-16【强制】禁止过早优化
❌ 禁止：
- 在正确性之前做缓存
- 不必要的异步
- 分布式设计

---

### CC-17【强制】可读性高于技巧
如果代码：
- 不直观
- 看起来“很聪明”
- 抽象层级过高

则必须：
- 写清楚为什么这么做
- 说明更简单方案为何不采用

否则：
- 视为技术债

---

## 10. 演进约束

### CC-18【强制】新功能不得破坏心智模型
新增功能必须：
- 回答“它是否让我更快找到东西？”
- 不增加理解成本

❌ 禁止：
- 仅因“功能完整”而增加复杂度

---

## 11. 执行规则

### CC-19【强制】违反约束即 Bug
任何违反本文件的代码：
- 不得合并
- 必须重构
- 不接受任何借口

---

## 12. 最终底线

### CC-20【最高优先级】系统服务真实生活
- 允许不完整数据
- 允许错误数据
- 不允许强迫用户“正确使用系统”

如果系统开始让用户感到负担，
说明设计已经失败，必须回退。
